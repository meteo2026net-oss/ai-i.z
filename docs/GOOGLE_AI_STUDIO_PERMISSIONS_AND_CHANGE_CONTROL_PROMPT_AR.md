# طلب تنفيذ نظام الصلاحيات وإدارة التعديلات والموافقات في AI I.Z

> **نوع المستند:** تعليمات تنفيذية موجهة إلى Google AI Studio  
> **الهدف:** جعل صلاحيات المستخدمين وتغييرات المشاريع واضحة ومضبوطة وقابلة للتدقيق.

## 1. المهمة

افحص نظام المستخدمين والصلاحيات والموافقات الموجود في مستودع AI I.Z، ثم أكمله ليصبح نظاماً مركزياً يحدد من يستطيع مشاهدة المشروع أو تعديله أو تشغيله أو نشره أو إدارة أعضائه.

لا تنشئ نظام أدوار شكلياً في الواجهة. يجب فرض الصلاحيات في Backend وقواعد البيانات، مع عرضها بوضوح للمستخدم في التطبيق.

## 2. الأدوار المقترحة

اعتمد الأدوار التالية كنقطة بداية، مع السماح لمالك المشروع بتخصيص الصلاحيات ضمن الحدود الآمنة:

| الدور | الصلاحيات |
|---|---|
| مالك المشروع | إدارة المشروع والأعضاء والصلاحيات والموافقات والعمليات عالية الأثر |
| مدير المشروع | إدارة المهام والإعدادات والأعضاء المسموح بهم، دون نقل الملكية |
| مطور | إنشاء وتعديل الملفات وتشغيل الاختبارات ضمن حدود المشروع |
| مراجع | قراءة التغييرات ومراجعتها وقبولها أو طلب تعديلها وفق السياسة |
| قارئ | مشاهدة المشروع والتقارير دون تعديل |
| وكيل AI | تنفيذ المهام المفوضة فقط وبنطاق ومدة محددين |

لا تمنح وكيل الذكاء الاصطناعي صلاحيات مالك المشروع. صلاحياته مؤقتة ومحددة بالمهمة.

## 3. صلاحيات دقيقة قابلة للفهم

افصل الصلاحيات إلى إجراءات مستقلة:
- عرض المشروع والملفات.
- إضافة ملفات أو تعديلها.
- حذف الملفات.
- إنشاء فرع أو Commit.
- دفع التغييرات إلى GitHub.
- إنشاء Pull Request أو دمجه.
- تشغيل البناء والاختبارات.
- تشغيل أوامر في بيئة التنفيذ.
- قراءة مخطط قاعدة البيانات.
- تنفيذ استعلامات قراءة.
- تعديل بنية قاعدة البيانات أو البيانات.
- إدارة مفاتيح التكامل.
- إضافة الأعضاء أو إزالتهم.
- تغيير الأدوار.
- الموافقة على العمليات الحساسة.
- النشر إلى بيئة اختبار أو إنتاج.
- حذف المشروع أو تصدير بياناته.

يجب أن تكون الصلاحيات قابلة للتقييد حسب المشروع والفرع والبيئة والموارد، وليس حسب الدور فقط.

## 4. مستويات المخاطر والموافقة

اعتمد التصنيف التالي:

**المستوى 0 — قراءة:** عرض معلومات مسموح بها. لا يحتاج موافقة إضافية إذا كان المستخدم مخولاً.

**المستوى 1 — تغيير قابل للمراجعة:** تعديل ملفات داخل مساحة عمل أو إنشاء فرع. يسجل التغيير ويوفر إمكانية التراجع.

**المستوى 2 — تنفيذ محدود:** تشغيل اختبارات أو بناء أو مهام معزولة. يتطلب صلاحية تنفيذ وحدود موارد واضحة.

**المستوى 3 — أثر خارجي:** دفع تغييرات إلى مستودع بعيد أو تعديل خدمة أو قاعدة بيانات مشتركة. يعرض Diff أو خطة التنفيذ ويطلب موافقة الشخص المخول.

**المستوى 4 — أثر عالٍ أو غير قابل للعكس بسهولة:** حذف بيانات أو تغيير ملكية أو صلاحيات عليا أو نشر إنتاج أو ترحيل حساس. يتطلب موافقة صريحة منفصلة، وتأكيداً إضافياً، ونسخة احتياطية أو خطة استعادة عندما تكون ممكنة.

لا تعتبر موافقة عامة واحدة إذناً دائماً لكل العمليات. الموافقة مرتبطة بطلب واحد محدد.

## 5. شاشة إدارة الصلاحيات

أنشئ شاشة واضحة تعرض:
- أعضاء المشروع.
- دور كل عضو.
- الصلاحيات الفعلية لكل عضو.
- الصلاحيات المخصصة والاستثناءات.
- تاريخ منح الصلاحية وانتهائها.
- من منحها.
- آخر استخدام للصلاحية.
- طلبات الوصول المعلقة.
- سجل تغييرات الأدوار.

استخدم لغة مفهومة. مثال: «يمكنه تعديل ملفات المشروع وتشغيل الاختبارات، لكنه لا يستطيع نشر التطبيق أو حذف المشروع».

وفّر صفحة تفاصيل لكل دور مع شرح «ماذا يستطيع هذا الدور أن يفعل؟» و«ما الذي لا يستطيع فعله؟».

## 6. شاشة طلب الموافقة

عندما يحتاج الوكيل أو المستخدم إلى موافقة، اعرض بطاقة تحتوي:
- اسم العملية.
- سبب الحاجة إليها.
- المشروع والفرع والبيئة المستهدفة.
- الملفات أو البيانات التي ستتأثر.
- ملخص التغييرات قبل وبعد.
- مستوى المخاطر.
- هل يمكن التراجع؟
- التكلفة المحتملة إن وجدت.
- الوقت المتوقع إن أمكن تقديره.
- اسم الدور المطلوب للموافقة.

الأزرار:
- «موافقة وتنفيذ».
- «رفض».
- «طلب تعديل».
- «عرض التفاصيل».

لا تجعل الموافقة تنفذ تلقائياً قبل التحقق من الصلاحية على الخادم. لا تسمح لصاحب الطلب بالموافقة على طلبه إذا كانت السياسة تتطلب موافقاً آخر.

## 7. سجل التعديلات والمراجعة

أنشئ سجل تغييرات موحداً يشمل:
- من طلب التعديل.
- من نفذه: مستخدم أم وكيل.
- الوقت.
- الملفات والموارد المتأثرة.
- وصف التغيير.
- رابط Commit أو Pull Request إن وجد.
- نتيجة الاختبارات.
- الموافقة المرتبطة.
- إمكانية عرض Diff.
- حالة التراجع.

يجب ألا يستطيع المستخدم العادي تعديل سجل التدقيق أو حذف أثر العملية.

## 8. إدارة تغييرات الوكيل الذكي

قبل أن يغير الوكيل ملفات المشروع:
1. يقرأ الملفات ذات الصلة ويفهم البنية الحالية.
2. يحدد الملفات المتوقع تعديلها.
3. يشرح سبب كل تغيير.
4. يوضح أثر التغيير على الوظائف الحالية.
5. ينشئ نسخة عمل أو فرعاً مناسباً.
6. ينفذ التغيير في نطاق محدد.
7. يشغل الاختبارات ذات الصلة.
8. يعرض الفرق والنتائج.
9. يطلب الموافقة إذا كان التغيير يتجاوز صلاحياته.
10. يسجل النتيجة في سجل المشروع.

إذا اكتشف الوكيل حاجة إلى تغيير خارج نطاق المهمة، يتوقف عن ذلك الجزء ويقدم طلب موافقة جديداً بدلاً من توسيع صلاحياته تلقائياً.

## 9. التحقق التقني الإلزامي

- نفذ فحص الصلاحية في كل API محمي.
- لا تعتمد على إخفاء الأزرار في Android.
- لا تثق بالدور أو userId المرسل من العميل دون تحقق.
- اجعل صلاحيات وكيل AI مؤقتة ومحددة بالمشروع والمهمة.
- ألغِ التفويض عند انتهاء المهمة أو انتهاء المهلة.
- اربط الموافقة ببصمة محتوى التغيير أو معرف خطة ثابت حتى لا تتغير العملية بعد الموافقة.
- ألغِ الموافقة إذا تغيرت الملفات أو الموارد أو البيئة المستهدفة.
- امنع إعادة استخدام الموافقات.
- اختبر حالات الرفض وانتهاء الصلاحية وتعارض الصلاحيات.

## 10. الاختبارات

أنشئ وشغّل اختبارات تثبت:
- القارئ لا يستطيع التعديل.
- المطور لا يستطيع نشر الإنتاج دون موافقة.
- مدير المشروع لا يستطيع نقل الملكية.
- وكيل AI لا يستطيع منح نفسه صلاحية.
- المستخدم غير المخول لا يستطيع الموافقة.
- الموافقة لا تصلح بعد انتهاء صلاحيتها.
- الموافقة لا تصلح بعد تغيير محتوى العملية.
- سجل التدقيق لا يمكن تغييره من العميل.
- حذف الملفات والبيانات محمي وفق مستوى المخاطر.
- تغيير الدور ينعكس على الطلبات الجديدة فوراً.

## 11. معايير القبول

- توجد مصفوفة صلاحيات موثقة ومطبقة.
- لكل مشروع أعضاء وأدوار وصلاحيات واضحة.
- كل عملية حساسة لها طلب موافقة قابل للتتبع.
- لا يمكن تجاوز الصلاحيات بتعديل واجهة التطبيق أو طلب API مباشرة.
- يمكن عرض تاريخ كل تعديل ومراجعته.
- توجد اختبارات إيجابية وسلبية منفذة.
- لا تتغير الملكية أو الصلاحيات العليا دون موافقة مناسبة.

**نفذ النظام داخل التطبيق والخادم وقواعد البيانات الموجودة. حافظ على الصلاحيات الحالية إن كانت صحيحة، وعالج التعارضات مع توثيقها، ولا توسع صلاحيات أي دور تلقائياً.**
